# 火花规划器 UI/UX 设计规范

本规范约束新增及修改的全部页面、弹窗、表单、列表与交互。复用现有正确实现，每次 UI 改动都必须按文末清单验收。参考酒馆原生及成熟插件的交互组织方式，颜色始终适配酒馆当前主题。

## 1. 先组织用户任务

设计前回答：用户为什么打开这里、最常阅读什么、最常执行什么、哪些属于低频管理或技术调试、哪些可以合并或折叠。按完成任务的顺序安排首屏，不按数据字段或代码模块逐行铺开。

当前页是创作工作台：紧凑运行控制与包摘要 → 选材 → 创作指导 → 折叠材料 → 折叠原始输出。技术排查从更多菜单进入单轮诊断；全局配置在设置中。不得新增无必要的主页面。

## 2. 文字及空间层级

- 页面标题约 15–16px、中等字重；区域标题约 14px、中等字重。
- 正文、字段名、普通条目正常字重；辅助摘要约 12px、弱化但保持可读。
- 异常只有需要用户处理时才强调；正常状态用简短结论，如“默认版本 · 已生效”。
- 面板内边距 12px，区域间距 16px，字段间距 10px，字段名与控件间距 4px，工具栏间距 6–8px；窄屏可以适当收紧。
- 使用段落与留白分区；不为每一块再套卡片、边框和随机分隔线。辅助信息不与创作正文争夺注意。

## 3. 相关元素就近组织

同一对象的标题、状态与辅助操作组成紧凑区域：标题左、操作右；搜索、筛选、新增构成工具栏；列表行的开关、名称、状态与编辑入口边界清晰；渠道名与模型名同行，必要时换行。

长文本框下方共用一行工具栏：左侧无边框“放大、清空”，右侧 `Token：398` 或 `≈Token：398`。不得因为功能由独立组件实现就单独占满一行。不显示字数。空间不足允许换行，保持触摸目标至少约 36px。

复选框与其标签同行。辅助操作贴近所属内容，避免误点相邻条目。

## 4. 操作层级与列表入口

一个操作区域通常只突出一个主要操作：保存、确认应用或继续生成。次要操作使用普通、文字或轻量图标按钮；复制、放大、刷新不使用独占整行的大按钮。

复制包、导出、重命名、删除、调试等低频操作进入更多菜单或编辑器。删除使用适度危险样式和明确确认。不能以减少按钮为由删除功能。

列表主体可直接查看/编辑；不要每行重复“查看、编辑、删除、测试”。开关和排序与主体点击保持清晰边界。桌面可用鼠标、键盘和右键；移动端长按只做辅助入口，正常滑动不得触发长按。

## 5. 阅读与编辑分离

指导、历史、注入材料和说明使用普通文本或安全 Markdown。完整内容随页面主滚动区域展开，不用固定小 textarea 阅读。创作原文保持段落、列表及格式；复制只复制当前所见原文，不夹带 UI 标题、统计或说明。

编辑才使用 textarea。所有长文本编辑支持鼠标/触摸拖高、放大及统一 Token 工具栏。Token、模型匹配及普通状态刷新不得覆盖内容、手动高度、光标、选区或滚动。指导编辑提供保存/取消，保存写入新草稿，不改历史。

普通说明、只读诊断和预览不显示放大编辑或 Token 计数。

## 6. 内容决定窗口尺寸

- 大型：主面板、素材编辑器、长文本放大、本轮选材、大型注入/历史阅读和运行诊断，约可用视口 90%。固定标题与必要底栏，中间滚动。
- 普通配置：API 渠道、组合配置、模型规则、普通参数，内容自适应，最大约 90%。短内容不填空白；超出才滚动。
- 小型：新建分类/包、重命名和确认，只有必要字段与操作。

原生弹窗负责嵌套与最上层 Escape/返回。编辑器保留一个关闭入口及底部保存/取消；只读窗口保留一个返回入口。关闭面板不等于停止请求。未保存编辑要保护，关闭子窗返回父页面原位置。

## 7. 滚动、状态与异步

每个主要页面只有一个纵向主滚动容器。分类、模块、设置及数百条素材均参加整页滚动；分类不另建滚动区。textarea 保留文本滚动，但不能永久困住外层滚动。触摸拖高只捕获手柄上的手势。

切页、开关子窗、保存素材、Token 更新、模型变化和生成状态变化要保留搜索、筛选、分类展开、滚动、浏览包和焦点。优先按稳定标识更新或比较数据签名；不要为无关状态刷新重建整页 DOM。

异步操作显示真实加载、成功和失败，只锁相关控件。生成期间允许浏览、编辑资产；已发出的请求使用其冻结版本，后续编辑用于下一次请求。低风险操作简短反馈，不添加额外确认。删除、覆盖自定义 Prompt、切换资产来源保留确认。

## 8. 正常简洁，说明按需

正常状态只显示用户需要的结论；开启却不能生效时再给原因。世界书机制、预览范围、模型规则放在对应区域的简短帮助或诊断中。一次性迁移提醒只在确需处理时显示。

模型创作正文、用户阅读/编辑界面、程序配置与诊断是不同层次。不得把 JSON、内部 ID、API 参数或长篇技术说明混入创作正文。原始输出只展示模型实际返回的可见文本；程序诊断进入独立窗口。

## 9. 证据与数据保护

“预计注入/装配快照”不能称为“实际注入”。最终请求捕获要标明边界、角色、顺序和所属聊天/轮次/请求/回复版本。未捕获、已清理、不可归属分别说明；原因未知就说未知，不猜预算或裁剪。

只有可靠的逐来源追踪才能确认每项实际注入。精确文本出现和世界书激活只作为各自阶段证据，不等价于来源归属。禁止模糊相似度推断。无法可靠追踪时显示“实际注入记录不可用”，保留预计材料和可用的最终请求诊断。

复制全部材料保留该装配/请求的原始顺序和模型可见包装；阅读排序不能改变复制顺序。原始输出不随指导编辑变化。guidance 只取完整有效标签内部；手写指导无需标签。

请求诊断只保留明确允许的正文与参数；不记录认证头、URL 中的密钥、API Key 或 secretId。完整请求按明确范围保留，清理新增诊断正文不删除历史记录或创作资产。测试只用隔离数据及本地 Mock，不额外调用 AI。

## 10. 每次 UI 修改的验收

- 首屏是否以用户最重要的内容为主？辅助操作能否同行？是否存在重复入口、说明、边框或大按钮？
- 是否增加无意义纵向空间？任务步骤是否能减少？阅读、编辑、诊断是否清楚分离？
- 360/390/430px 及桌面布局是否溢出？长模型 ID/标题/包名是否自然换行？窄屏双列是否退化？
- 是否验证分类长列表滑动、标签长按与滑动区分、文本拖高、嵌套返回、焦点和滚动保留？
- 真机软键盘、横竖屏及主题若未验证必须说明，不能把模拟视口说成真机验收。
- 是否回归自动/审核/手动、生成中编辑、世界书状态、包归属、历史复用、guidance 提取、Planner 请求与 Generation 注入？
- 未改变自定义 Prompt 与创作资产；未泄漏认证；尚无证据的阶段不伪造成功。

“所有按钮都还在”不能代替上述验收。后续新组件也必须沿用这些原则。
